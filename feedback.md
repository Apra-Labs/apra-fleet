However the opt-out check is not actually wired to the repo being queried, which breaks the task's own done-criterion "getProvider() checks repo-level config before resolving provider" for real usage. src/tools/code-intelligence.ts:82 defines `getProvider(repoPath: string = process.cwd())`, but every call site in src/index.ts (code_graph ~L377, code_impact ~L384, code_query ~L389, code_context ~L394-399, code_map ~L404, code_flow ~L409, code_tests ~L414) calls `getProvider()` with NO argument, so repoPath always defaults to the MCP server process's own cwd -- never to `input.repo`, the field every one of these tool schemas documents as "Absolute path to the repository root. Required when multiple repositories are indexed." The underlying providers (code-intelligence-gitnexus.ts, code-intelligence-codebase-memory.ts) already route per-call using `params.repo`, confirming this is a genuine multi-repo architecture. As wired, a repo with `enabled:false` can still be queried via e.g. `code_graph({repo: '<that repo>', symbol: ...})` as long as the server's own cwd isn't opted out, and conversely queries against every other repo get incorrectly disabled if the server's cwd repo happens to have opted out. This isn't covered by tests/code-intelligence.test.ts either -- its new test calls `getProvider('/some/repo')` directly, bypassing the index.ts dispatch path where the bug lives, so the gap wasn't caught. Fix: thread `input.repo` (falling back to process.cwd() when absent, matching the "without a repo param" convention used elsewhere in the providers) into `getProvider()` at all 7 call sites in src/index.ts, and add a test that exercises the disabled path through one of the actual tool handlers with a repo param rather than only through the bare getProvider() unit.
